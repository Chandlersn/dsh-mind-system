# dsh-mind-system

**DeepSeek Harness 心智系统** —— 一次装齐四个插件，让 agent 知道"遇到什么问题先问什么"。

不是四个工具的清单，是一条链：

```
用户的问题
   ↓
① dsh-agent-mind      判断顺序常驻提示 + 按处境把该看的工具推到眼前
   ↓                 （"什么时候用谁"被显式化，不再靠 agent 从平铺的工具表里猜）
② dsh-clis            判因果结构：环 / 对偶 / 单向 / 嵌套
   ↓                 （反复无效时，给尺子而不是给更多方案）
③ dsh-meta-framework  重新审视问题本身：重定义 → 边界 → 选择 → 观测
   ↓                 （"真问题可能不是字面问题"）
④ dsh-memory-manager  沉淀：五层判据守写入，判据反哺上一轮
                     （器 → 术 → 法 → 道，每层有边界有反面）
```

---

## 为什么做这个

DSH 的工具面是**平铺**的：几十个工具并排躺在提示里，每个都带一段描述。模型要自己从描述里分辨"此刻该用哪个"——这是一次没有辅助的临场判断，于是：

- **反复无效时换方案，而不是换判据**。指标来回震荡、越调越糟，模型继续换做法，而真正的问题是对因果结构的误判（是环、是对偶、还是单向）；
- **不知道的事与没做成的事混在一起**。"这个 API 怎么调"和"改了没效果"是两类问题，却都表现为"再试一次"；
- **判据写在文档里等于没写**。文档不读，模型不知道；写了不校验，改了就漂；
- **沉淀下来的东西没法被检验**。记了一堆结论，但没人知道哪条还成立、哪条早被推翻了。

心智系统把这四件事变成机制。

---

## 适合 / 不适合

**适合**：想让 DSH 上的 agent 在**多步、反复、容易走偏**的任务上少走弯路的人。
尤其适合"改了很多次还是不对"这类场景 —— 心智系统的主要价值在**第二次尝试之后**才显现。

**不适合**：

- 单步问答、一次性脚本 —— 装它只是多占一点提示空间；
- 需要精确控制工具调用顺序的场景 —— 调度层只**重排不删除**，且有一拍延迟（见「已知限制」）；
- 已经在用别的记忆方案且不想换 —— `dsh-memory-manager` 会与既有记忆根冲突
  （同一 `~/.dsh/memory` 下不建议并存两套）。

## 安装

聚合包**装载四个成员**，是它们唯一的装载入口。

```bash
dsh plugin --profile web add dsh-mind-system
```

装完**重启宿主**（server 半边需要重新装载）。

### ⚠️ 别再单独装其中一家

聚合包已经装载了四家。再单独装某家，那家会被**装载两次**：同一 id 的装载点
由后者覆盖，仍能工作，但行为取决于装载顺序（实测：聚合包自己会被挤掉）。

只想要其中一家的能力时，从聚合包的 `bundles` 里移除其余即可 ——
或者直接单独装那一家（此时不要装聚合包）。

### 也可以分别安装

若你不想用聚合包，四家各自独立可用（各自有各自的 bundle patch）：

```bash
dsh plugin --profile web add dsh-agent-mind
dsh plugin --profile web add dsh-clis
dsh plugin --profile web add dsh-meta-framework
dsh plugin --profile web add dsh-memory-manager
```

此时**不要**再装聚合包（会双装载）。

### 少装会怎样

不是报错，是**降级**——这一部分能力不在，其余照常：

| 少装 | 后果 |
|---|---|
| `dsh-clis` | 判不了环/对偶/单向；meta 退化为通用重定义；系统监督消失 |
| `dsh-meta-framework` | 失去"重新审视问题"这一手 |
| `dsh-memory-manager` | 记忆写入无判据把关，蒸馏退回"写进去就算" |
| `dsh-agent-mind` | 工具平铺在提示里，agent 得自己从描述里分辨该用谁 |

## 依赖方向

```
        dsh-base（宿主提供 systemPrompt / tools 服务）
              │
    ┌─────────┼─────────┬──────────────┐
    ▼         ▼         ▼              ▼
 agent-mind  clis   meta-framework  memory-manager
    │         │         │              │
    │         └────────►│  取分类器     │
    │         （ctx.get）              │
    └──────────► 广播信号 ◄────────────┘
      mind/register-signal（外部 → 调度层）
```

- **clis** 是唯一的因果判据提供者。`meta-framework` 通过 `ctx.get('clis.causalClassifier')` 取它；取不到就退化为通用重定义（**降级而非报错**）。
- **agent-mind** 不 import 任何一家，靠两条广播通道通信：`clis/register-probe`（自己 → CLIS）、`mind/register-signal`（外部 → 自己）。
- **memory-manager** 自足。

用广播而非 import，是因为 import 会造成反向依赖 ——
"没装调度层就装不上 CLIS"是坏形态。

## 三种安装形态（各实测一次）

聚合包该怎么做，做过三种，各重启验证一次：

| 形态 | 实测结果 |
|---|---|
| 聚合包不装载四家 | 单独装 = 四家全都不在（`clis_probe` 消失） |
| 聚合包装载 + 四家也在 `bundles` | 双装载，**聚合包自己被挤掉**（user_plugins 14，mind-system 消失） |
| **聚合包装载 + 四家不在 `bundles`** | **唯一入口、零重复** ← 采用 |

## 四家各做什么

### dsh-agent-mind —— 调度层

往系统提示注入一段常驻的**判断顺序**（不是工具清单），并按当前处境**重排**工具面。

- 只重排、绝不删除：工具只有出现在声明里模型才知道它叫什么，藏掉它连问的机会都没有
- core 工具（文件/shell/搜索等）永不移动、永不延后载入
- 判断可解释：`mind_signals` 工具能回答"为什么这一轮排了这个顺序"
- 命中率可测：内置命中率回归（含一批**留白样本**专门检验泛化）+ 真实使用采样（趋势）
- 外部单元可贡献信号：CLIS 与 memory 各广播自己的领域词汇

### dsh-clis —— 判因果结构

四组件（classifier / strategy / feedback / orchestrator）+ 五工具。

- `clis_classify` 只判结构，`clis_run` 给匹配做法，`clis_plan` 只列做法与代价
- 介入机制带**漏判分母**：每次"放过"都记原因与闸门，`miss_rate` 可查
- 系统监督：只投递被监督者自己产不出的结论
- 向调度层广播因果词汇（`clis-causal`）

### dsh-meta-framework —— 重新审视问题

一个工具 `meta_reframe`，四层流程：重定义 → 边界 → 选择 → 观测。

- 描述问题而非判定问题：给重定义、边界与因果结构判断，不替你决定下一步
- 每次调用写 trace 可回放；退出码、失败记录都如实报告
- **它是诊断工具不是决策工具** —— 真实任务上会卡 `human_gate`，故只暴露诊断动作

### dsh-memory-manager —— 五层记忆

十四工具，五层结构：**器**（接触面）→ **术**（域内迭代史）→ **法**（跨域原则）→ **道**（最抽象命题）+ 技能（可调用程序）。

- 每层有**硬判据**：法要 ≥2 个**无关**来源域，道要 ≥5 条法萃取
- 每层有**边界**：说不出"何时不成立"即不合格
- 写入**前**拒绝 + 写入**后**回读复核，回执带 `selfCheck`
- 25 条体检判据（R0–R25 + F/TEMP）
- 向调度层广播记忆词汇（`memory-recall`）

## 配置

聚合包本身不接配置（它只是装载点）。配置给各成员：

```yml
# 记忆根与阈值（memory-manager）
- id: memory-manager
  name: 'dsh-memory-manager'
  config:
    memoryRoot: C:/Users/you/.dsh/memory
    maxIndexBytes: 10240          # 索引舒适线
    maxIndexHardBytes: 15360      # 索引硬上限，达到即拒写
    maxFunctionBytes: 30720       # 单个功能文件上限
    newFeatureGraceDays: 3        # 冷记忆宽限期
    recallTimeoutMs: 3000         # 前台召回预算（只能缩短不能延长）
```

完整配置项见各成员自己的 README。

## 健康探针

聚合包导出 `healthProbe`（供 dsh-clis 的监督层自动发现）。

聚合包**不提供任何能力** —— 它只是四家成员的共同装载点。但"某个成员没装上"
这件事此前**完全不可见**：宿主不报错（少装一家只是降级），聚合包自己没有
探针，`apply()` 又是纯 no-op。于是"装了个残缺的聚合包"没人知道。

| 代号 | 严重度 | 含义 |
|---|---|---|
| `mind-system.member-missing` | error | 声明的成员在本仓库里找不到 |
| `mind-system.ok` | info | 声明的成员都在 |

**它只说它能观察到的事**：探针是**零参数**调用的（拿不到宿主上下文），
所以只能检查成员包在磁盘上是否存在，**不能**声称它们在真宿主里已装载。
文案里写明了这一点 —— 观察不到的事实不说。

## 排错

| 症状 | 多半是 | 怎么办 |
|---|---|---|
| 聚合包装了，但四家都不在 | 聚合包与单独安装互斥 | 从 `bundles` 里去掉单独装的那家，或去掉聚合包 |
| `clis_probe` 报 `unknown tool` | CLIS 没装载成功 | 看宿主启动日志的 "did not activate"；多半是 `inject` 的依赖服务没就位 |
| 调度命中但工具面没变 | 一拍延迟（结构性） | 处境在下一轮生效，不是 bug |
| `mind_signals` 工具调不到 | 宿主没有 `dsh-tools` | 看 `mind` 的 warn 日志；工具降级但其它功能不受影响 |
| 改了插件代码，行为没变，也没报错 | 该包不在 HMR `root` 列表里 | 把它的真实物理目录加进 `cordis.patch.yml` 的 HMR `root`（**不能写 junction 路径**） |
| 改了 `server.js` 不生效 | 模块生成缓存以 realpath 为键 | 重启宿主 |
| npm 上 `dsh-mind` 装成了别人的包 | 名字被占用 | 用 `dsh-agent-mind` |

## 已知限制

- **调度有一拍延迟（结构性，不是缺陷）**：宿主 `preStep()` 的次序是
  `:907 assemble()` 先、`:909 agent/pre-step` 后，所以第 N 步读到的处境作用在
  第 N+1 步的工具面上。**不要试图"修"它** —— 那需要改动宿主时序。
- **命中率不是 100%，也不会是**：留白批门槛 60%、实测 80%。剩下的是真实表述的
  分布 —— 靠采样趋势盯着，无信号率走高就该扩词表。
- **`packages/dsh-clis` 是发布产物不是源码**：CLIS 真源码在独立仓
  `Chandlersn/dsh-clis`。改源码后要重新 `bundle.mjs` → `package.mjs` → 同步。
  这条链已踩过坑：**拷贝式打包不重建中间产物**，于是改的是源码、跑的是旧产物。
- **聚合包与单独安装互斥**（见安装章）。
- **`dsh-meta-framework` 未注册上游服务**：上游提供 `apply(ctx)` 把服务注册到
  宿主（`'causalLayers.metaFramework'`），本插件没接 —— 别的插件因此拿不到
  meta 的能力。这是一处已知缺口，不是设计。
- **HMR 监视范围是硬编码白名单**：不在 `root` 列表里的包改了不生效且无报错。

## 借鉴出处

| 借鉴 | 体现在 |
|---|---|
| **Hindsight 的 memory defence** | 记忆写入路径在落盘前把凭据形态替换成 `[REDACTED:kind]`；个人标识符只告警不改写 |
| **Hindsight 的 temporal recall** | `memory_search` 的 `after`/`before` 按日期区间过滤，命中带归属日期 |
| **Hindsight 的 observations** | 原则是"带证据的信念"：信任级由认可/纠正计数自动算出 |
| **MemOS 的前台预算与被动捕获** | `recallTimeoutMs` 绝对超时静默放行；`captureUserTurns` 默认关闭 |
| **自组织分层的思路** | 使用信号聚合出分层建议，**只建议不擅动** |
| **"信号在谁身上生成"** | 自产信号不给自己背书：先问"没人检查时这读数会不同吗" |
