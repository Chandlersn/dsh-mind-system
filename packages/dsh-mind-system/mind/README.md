# dsh-agent-mind · 编排系统

DSH 插件：把**"该用哪类工具"的判断顺序**装进系统提示，并让工具面跟着当下的问题走。

它做的是给已有的工具面装一个索引 —— 不是加工具，而是决定**谁先被看见**。

---

## ⚠️ 先读这一段：它解决的不是"工具不够"

本机的实测形态是两种，都不是缺工具：

1. **工具都在，但没人想起来用** —— `clis_metrics` 里 `hinted=0` 持续两周，
   监听器根本没注册，而指标看起来像"最近没人失败"
2. **用了，但用错层** —— 拿因果分析去做一次性的信息整理，
   输出只是把问题描述抄进模板（实测：非因果问题返回 `meta.observe_first` 这类空转候选）

缺的是**选择工具的那个判断**。所以这里写的不是"有哪些工具"（那在工具表里），
而是"遇到什么信号时，先问哪一类问题"。

### 适合 / 不适合

**适合**：工具多到"不知道该用哪个"的时候。本质是给平铺的工具面**加一个索引**，
不是加工具。

**不适合**：

- **单步任务**：处境判定要读本轮用户输入，一次性脚本用不上；
- **需要精确控制工具顺序的场景**：它只**重排不删除**，且效果依赖宿主与模型（见下）；
- **提示空间紧张**：常驻分节约 830 字 —— 在工具表已经很长时，这是一笔要算的成本。

## 它往系统提示里加什么

一个分节 `mind:orchestration`（order 2410），内容是四步判断顺序：

1. **这是"不知道该怎么办"还是"知道但没做成"？** 判据是能不能一句话说出下一步动作
2. **反复无效时先怀疑因果结构** —— 并明确写出反例：一次性信息整理、格式转换、
   纯查询这类问题判结构只会空转
3. **动手前先确认"这事以前是不是已经定了"** —— 涉及约定/常量/踩过的坑时先查记忆
4. **需要外部事实时分清"找"和"读"** —— 搜索只给候选，不给正文

每条都带**反例**。只说"什么时候该用"的索引会诱使 agent 到处套用；
必须能说出"调了也没用"的情形。

分节点名六件工具，让"先看谁"有具体落点：

| 工具 | 为什么点它 |
|---|---|
| `clis_classify` | 判因果结构 |
| `clis_run` | 给匹配做法（写动作需显式放行） |
| `clis_plan` | 只列做法与代价 |
| `memory_read` / `memory_search` | 先查再动 |
| `meta_reframe` | 觉得问题本身问错了时，先重定义 |

## 它怎么让工具面跟着处境走

```
agent/inbox/claimed ──看本轮消息──▶  判处境（diagnose/execute/recall/retrieve/unknown）
                                              │
system-prompt/assemble ──读处境────────────▶  重排 assembly.tools
```

五种处境把对应工具族排到前面：

| 处境 | 何时进入 | 工具面怎么变 |
|---|---|---|
| `diagnose` | 解法未知、反复无效、分不清因果 | 判据工具提前 |
| `execute` | 知道要做什么，只差动手改 | 动手类工具提前 |
| `recall` | 涉及既有约定/踩过的坑 | 记忆工具提前 |
| `retrieve` | 需要外部事实 | 检索工具提前 |
| `unknown` | 判不出来 | 什么都不做，保持默认顺序 |

并有一条**硬约束**：

> **只重排，绝不删除。** 少了声明，模型连工具名都看不到 —— 那是能力损失。
> 重排只影响注意力顺序，任何工具都还在，随时可调。

同时**核心工具永不动**（文件/shell/协作类）：判断标准不是"现在用不用得上"，
而是"这个处境里如果突然要用，藏了它会不会把人卡住"。

### 两个刻意的设计

- **处境 unknown 时什么都不做**：宁可保持默认顺序，也不凭猜重排
- **`deferLoading` 缺省关**：重排是纯顺序、零风险；给异族工具打
  延后载入标记会让声明不常驻、效果依模型适配器而异。有风险的那半做成
  显式开关（`DSH_MIND_PARK=1`），默认只交付无风险的那半

### 为什么用 `agent/inbox/claimed` 而不是 `agent/pre-step`

宿主 `preStep()` 的次序是：

```
:906  claim()      ← 拿到本轮输入，并发出 agent/inbox/claimed
:907  assemble()   ← 工具面在此定稿
:909  agent/pre-step  ← 处境在此才判出
```

早期版本在 `agent/pre-step` 里判处境，于是**重排永远晚一步**：

- 第 1 步（模型第一次回应用户、决定用哪个工具的那一步）用的是默认顺序
- 第 2 步用上了第 1 步判出的处境 —— 但模型已经在干活了
- 第 2 步起 inbox 为空 → 处境被重置 → 第 3 步又变回默认顺序

一个 turn 内工具面**变动两次**。而宿主的 `headerEquals` 是**按顺序**比较
工具面的（`dsh-session/lib/types/request-header.js:44`），顺序一变就判"工具面
变了" → `startsSeries=true` → 全部系统提示节点被替换 → **请求序列重启、
提示缓存前缀作废**。收益在第 1 步（没有），代价在第 2 步（全付）。

`agent/inbox/claimed` 在 `claim()` 里发出，**早于** `assemble()`，且携带用户
消息本身 —— 工具面定稿时处境已经就位，重排能作用于第 1 步。

`agent/pre-step` 保留为**兜底**：老宿主没有 `inbox/claimed` 时仍可采样并影响后续装配，但首步已经装配，可能滞后一拍。

## 调度机制：三个能力

处境判定不是写死的关键词匹配，而是**可注册、可解释、可记账**的机制
（`src/dispatch.js`）：

| 能力 | 说明 |
|---|---|
| **信号可注册** | 任何单元贡献自己的处境信号，带词表、**反例词**、权重、归属 |
| **判定可解释** | `explainSituation()` 返回命中了哪些、落选哪些、各命中几处 |
| **命中可记账** | 探针区分"调度没生效"与"本轮无信号"（两者原本同形） |

内置 14 条信号，按**判断依据的种类**分五族：

| 族 | 判据 | 典型词 | 指向 |
|---|---|---|---|
| **症状族** | 事情没成 | 没效果、无效、反复、还是不行 | `diagnose` |
| **意图族** | 我在问什么 | 评估、审查、完善、有没有、靠谱吗 | 先看而非先动手 |
| **报错族** | 直白的问题陈述 | 写错了、不对、报错、失效、崩了 | `diagnose` |
| **元问题族** | 问系统自身效果 | 实测效果、账本、命中率、漏判率、信号词典 | `diagnose`（先查账本，不能凭印象） |
| **视觉缺陷族** | 用户描述看到的问题 | 遮挡、被裁、重叠、混到一起、同屏 | `diagnose`（先看实镜，不猜设计） |

后三族是 2026-11-10 从**真实漏判**补进来的，每族在源码里带 `source` 字段，记着
"这个词从哪次事件来"——见下方「信号词典可积累」。

反例词让信号能自己否定自己 —— "这个测试**反复**失败"里的"反复"指测试自身，
不该触发诊断；"如果不对就修正"里的"不对"是条件句，不该判成报错。

### 信号词典可积累（2026-11-10）

用户的要求是：**把关键词和它来自的事件建立映射，让词典能自己长大**。
所以每个信号可以带一个 `source`：

```js
registerSignal({
  name: 'visual-defect',
  words: ['遮挡', '被裁', '重叠', '混到一起'],
  counterWords: ['区间重叠', '范围重叠'],
  source: '2026-11-10 用户两次漏判：「按钮文本有被遮挡」「页面都不同，混合重叠显示了」',
})
```

`listSignals()` 能回查每个信号的出处。只有词表没有出处，半年后没人知道
某个词为什么在这儿、能不能删，词表就烂成谁都不敢动的祖传常量。

**扩词的硬规则**（实测定下）：加词必须同时跑既有用例。给「视觉缺陷族」
加「越界」时，`把越界判断修好` 从 `execute` 变成了 `diagnose` —— 在代码
语境里「越界」几乎总是业务含义（边界检查），不是 UI 溢出。

采样文件里，**未命中行**（`no-signal` / `ambiguous`）会额外记一条 ≤60 字的
**脱敏摘要**（路径 / URL / 凭据 / 长 hex / 代码片段都替换成类型标记后截断），
于是"该加什么词"可以事后回查，而不是靠人当场记住。命中行不记输入。

### 外部单元可以贡献信号（零配合）

编排系统原本只有自己写的词表，于是**各插件自己领域的词汇全是盲区** ——
实测「判一下这个是不是回路」「因果结构」「对偶」「沉淀」「五层」全部无信号，
而这些恰是各插件最该被用上的时刻。

现在各家经 `mind/register-signal` 广播自己的词汇：

| 谁 | 信号 | 词表 |
|---|---|---|
| `dsh-clis` | `clis-causal` | 因果、结构、回路、反馈环、对偶、矛盾、归因、根因… |
| `dsh-memory-manager` | `memory-recall` | 沉淀、蒸馏、五层、层级、边界、反面、约束条件… |

**广播没有方向性** —— 缺编排系统时这条广播无人接收，CLIS 照常工作。
（直接 import 会让 CLIS 反向依赖编排系统，于是"没装编排系统就装不上 CLIS"。）

## 行为策略（2026-11-03）

下面这张表是插件**实际会做的判断**，不是设想。每一行的"验证方式"都指向
一条真的跑过的断言或实验，不是"应该没问题"。

| 场景 | 触发条件 | 不触发条件 | 预期引导 | 生效位置 | 优先级 | 验证方式 |
|---|---|---|---|---|---|---|
| `diagnose` 判结构 | 症状词（没效果/反复/震荡/还是不行）或意图词（评估/审查/是不是/靠谱吗） | 用户明确说"别做因果分析" | 判结构工具排前 | `assemble.tools` 顺序 | 症状族权重 3 > 意图族 2 | `policy.test.js` + 对照实验 |
| `execute` 动手 | 动作词（修改/改成/修复/部署）或意图词（完善/整理/生成） | 否定辖域覆盖该动作；或"别动代码" | 动手类工具排前 | 同上 | 被否决时整类作废 | `policy.test.js` |
| `recall` 先查记忆 | 以前/上次/约定/踩过 | "别查记忆" | 记忆工具排前 | 同上 | 同上 | `policy.test.js` |
| `retrieve` 取外部事实 | 搜一下/最新/文档/论文 | "别搜了" | 检索工具排前 | 同上 | 同上 | `policy.test.js` |
| **不触发** | —— | 短输入、闲聊、纯格式转换 | 不动工具面 | 无 | —— | 断言 `unknown` |
| **歧义** | 两类处境得分差 < 15% | —— | **不动工具面**（克制闸门） | 无 | 高于一切引导 | `policy.test.js` |
| **用户明确指令** | "别做 X" / "别动 Y" | —— | 否决该处境，**用户优先于插件推断** | 信号层整类作废 | 最高 | `policy.test.js` |

### 判断前先做归一化，而不是往词表里堆词

实测 18 条真实语料，旧实现判错 3 条，全部落在同一族缺陷上 —— 不是词不够多，
是**匹配之前缺一层归一化**：

```
「不用审查，直接跑测试就行」        → diagnose   （否定词没管到意图族）
「不要整理，也不要汇总，直接贴日志」 → execute    （"不要整理"里的"整理"仍命中）
「注释写着"修复登录超时"，请解释它」  → execute    （引号内是被引用文本，不是指令）
```

现在做成四条**具名规则**，每条可单独测试、在诊断里单独计数：

| 规则 | 剥掉什么 | 为什么 |
|---|---|---|
| `quoted` | 引号 / 代码跨度 | 被引用的文字是**提及**，不是**指令** |
| `negated` | 「否定词 + 可请求动作」跨度 | 「不要修改 A，修复 B」须保住 B |
| `conditional` | 「如果…的话」假设从句 | 假设不是请求 |
| `vetoed` | 整类处境（用户明确排除） | **用户明确指令优先** |

两条边界写在这里，因为它们是刻意的取舍，不是遗漏：

- **否定只作用于动作词**（修改/审查/整理…），不作用于事实描述（无效/反复）。
  用户能"不要"的是行为，不能"不要"的是事实。所以「没有效果」不会被自己的
  "没有"剥掉 —— 这个安全性由**作用域**保证，不靠砍否定词。
- **只剥带 `的话` 的条件句**。「如果要改就改这里」里的请求恰恰在从句里，
  剥掉就把用户要的事弄丢了。宁可少做，不要做错。

### 判不出要分四种，不能都报成 unknown

| `reason` | 含义 | 该怎么处理 |
|---|---|---|
| `matched` | 判出了一个处境 | 正常 |
| `ambiguous` | 两类势均力敌 | **不引导**，它需要更好的判断力，不是更长的词表 |
| `no-signal` | 有内容但没信号命中 | 这是**词表**的缺口 |
| `nothing-actionable` | 归一化后没内容（空 / 过短 / 全是引用） | 这是**输入**的性质，**不该拿去扩词表** |

旧实现把后两者混成一个 `unknown: true`，于是"该扩词表"与"这条本来就没法判"
在观察上同形 —— 拿错的那批去扩词表，只会把词表撑坏。

## 三级诊断：判断 / 提供 / 照做

任务书要求区分三件事，它们在本插件里**分开记账、互不冒充**：

| 级别 | 含义 | 数据来源 | 什么时候是 `null` |
|---|---|---|---|
| 1. 判断 | 插件判出了什么 | `situations.lastDecisionOf(agent)` | 还没见过任何用户输入 |
| 2. 提供 | 插件**真的**据此重排了工具面 | `assemble` 里 `recordGuidance()` | 判成 unknown / ambiguous / 事件缺失 |
| 3. 照做 | 模型**实际**用了该族的工具 | `tools/result` 事件观察 | **没提供过引导** → 恒 null，不是 false |

第 3 级的判据用 `isFamilyTool()`（与 `arrangeTools` 同一份族清单）。
诊断若自己再写一份 `startsWith` 判断，两份漂移之后就会开始谎报"已照做"。

`followed` 的语义要特别读清楚：

- `null` = **没观察**（没提供引导，或本轮没有工具调用）—— 不是"没照做"
- `true` / `false` = 真的比对过

把"没观察"报成"没照做"，就是拿缺失当阴性证据。

### 隐私

诊断与采样**不保存用户原文**：

- 归一化只留**计数**（剥了几处引用/否定/条件），不留任何片段
- 工具调用只记**名字**，不记参数（参数里有路径、密钥、用户数据）
- 采样文件只存时间、处境代号、命中信号名

`mind_signals` 工具返回的 `diagnosis.normalization` 就是那组计数 ——
维护者能看出"这次剥了 2 处否定"，但看不到用户说了什么。

## 信号覆盖与分类准确率

采样统计非空用户输入中有多少命中至少一条信号，这叫**信号覆盖率**，不是分类正确率。高覆盖率也可能包含误判；无信号也不一定代表任务失败。每日记录中提取的用户原话没有标准标签，且无法证明未参与词表调整，因此不能称为留出集或泛化准确率。

对有人工标签的样本，`hitRate()` 单独返回 `accuracyRate` 和标签数；无标签时正确率为 `null`。旧字段 `rate` 为兼容保留，混合有无标签样本时不能解释为准确率。

采样只保存时间、判定处境、命中信号名；**未命中行**额外保存一条 ≤60 字的脱敏摘要（路径 / URL / 邮箱 / 凭据 / 长 hex / 代码片段替换成类型标记后截断），命中行不存输入。不保存原文，也不保存可反查的稳定哈希。设置 `DSH_MIND_SAMPLING=0` 可关闭新采样。历史文件不会自动删除，旧版本记录的哈希仍可能通过猜测比对识别。采样文件持续增长，需按本地数据管理策略清理。

## 输出与副作用

| 项 | 值 |
| --- | --- |
| 系统提示分节 | `mind:orchestration`，order 2410 |
| 工具 | `mind_signals`（只读，见下） |
| 状态 | 只读处境 + 重排装配结果，不写任何文件（采样除外，见下） |
| 采样文件 | `<DSH_HOME>/storages/mind-dispatch-samples.jsonl` |
| 降级 | 监听器注册不等于事件已发出；旧宿主的 pre-step 兜底可能滞后一拍 |

### `mind_signals`（只读）

查调度此刻覆盖了哪些词、谁贡献的、上次判定命中了什么。

**为什么需要它**："外部单元到底贡献了没有"原本看不出来 ——
探针 message 被监督层压缩成代号，进程外的脚本读不到运行时注册的信号。
结果是"机制可用但生态为空"与"生态已长出来"在观察上完全同形。
这个工具把那个区分变成一条命令。

## 健康探针

| 代号 | 严重度 | 含义 |
| --- | --- | --- |
| `mind.not-loaded` | error | 没跑到 `apply()`（inject 未满足 / 模块加载失败） |
| `mind.section-missing` | error | `systemPrompt` 不可用 → 判断顺序不会出现在提示里 |
| `mind.orchestration-missing` | info | 编排事件不可用 → 工具照常可用，但不会按处境重排 |
| `mind.dispatched` | info | 调度命中：处境 + 命中的信号名 |
| `mind.no-signal` | info | 调度已接上，但本轮没命中任何信号（**正常状态，不是故障**） |
| `mind.trend` | info | 采样趋势：累计次数、无信号率和信号覆盖率 |
| `mind.benchmark` | info | 每日记录中用户原话的信号覆盖率；不代表准确率或独立留出集 |
| `mind.event-status` | info | 已观察到 claimed、使用了兜底，或事件尚未验证 |
| `mind.signals` | info | 信号清单：内置几条、外部贡献几条（各 owner 一条独立代号） |
| `mind.guidance-issued` | info | **第二级**：已向 DSH 提供引导（工具面真的按处境重排了） |
| `mind.guidance-withheld` | info | **第二级**：判定已作出但未提供引导（unknown / ambiguous 克制 / 事件缺失） |
| `mind.guidance-followed` | info | **第三级**：观察到模型采用了引导推荐的工具族 |
| `mind.guidance-not-followed` | info | **第三级**：观察到工具调用，但不属引导推荐的族 |
| `mind.guidance-unobserved` | info | **第三级**：已提供引导但本轮无工具调用 —— **无法判断，不等于没照做** |
| `mind.ok` | info | 正常 |

`guidance-*` 五个代号对应任务书要求区分**三件事**：插件判断了什么（`mind.dispatched`）、
插件提供了什么引导（`issued` / `withheld`）、模型实际做了什么（`followed` / `not-followed` /
`unobserved`）。**前两级不能冒充第三级**：

- `followed` 为 `null` 表示**没观察**（没提供引导，或本轮没调工具），**不是** `false`
- 「模型没照做」不是插件故障，所以这五条严重度全是 `info`，不拉红灯
- `withheld` 长期出现才值得怀疑判据，单次是刻意的克制

编排缺失标 `info` 不拉红灯（它是增强），但**必须报出来** —— 否则
"编排没生效"与"编排生效了但这一轮处境是 unknown"在观察上完全同形
（都是工具面没变化）。

外部信号按 **owner 发独立代号**（`mind.signal-from-<owner>`）——
监督面只输出代号不转发 message，所以数字必须编码进代号才看得见。

`mind.trend` 与 `mind.benchmark` 都是**同步**读出来的 —— 探针是同步函数，
返回值当场定型。早期版本在 Promise 里 push 那条 finding，监督层拿到的
定型快照里根本没有它 —— 那条读数**从未出现过**。

## 开发

```bash
npm test                        # 单元与真实宿主接线用例（分节 / 编排 / 调度 / 命中率 / 采样 / 接口 / 接线集成）
node scripts/verify-assembly.mjs # 对真实 systemPrompt 服务验证（推荐先跑这个）
```

`verify-assembly.mjs` 装载**真实的** `@deepseek-ai/cordis` 与
`@deepseek-ai/dsh-system-prompt`，调 `assemble()` 检查：

- 分节真的进了装配结果（不是"我调了 section()"）
- 工具面重排真的落到装配结果，且与"不装本插件"的基线逐字相同（未判处境时）
- **重排在第 1 步就生效**（不是滞后一拍）
- **空输入后工具面保持不变**（一个 turn 内只变一次，不抖）
- 工具数量与名字集合不变（能力零损失）
- 卸载后分节消失

⚠️ 这个脚本**必须提供 `tools` 服务**（mind 的 `inject` 是
`['systemPrompt', 'tools']`）。缺了它，`apply()` 不会被调用、插件不激活，
分节不注册、编排不生效 —— 脚本会报 5 项 FAIL 而插件看起来"没坏"。
它现在也在测试套件里（`test/integration.test.js`），跑不掉。

单测用假 ctx，只能证明"调用发生在"；这个脚本证明"下游真的接上了"。
两者的差距正是本机反复踩过的那类缺陷。

`test/integration.test.js` 用**真实 cordis** 装载插件，走宿主同一条路径，
钉住"宿主接线"这一层 —— 旧套件删掉 `agent/pre-step` 或
`system-prompt/assemble` 监听器仍然全绿，那就是这条缺口。

## 依赖

- `@deepseek-ai/cordis`（peer，optional）—— 运行时从 DSH 安装目录 require
- `@deepseek-ai/dsh-system-prompt` —— 由宿主 dsh-base 提供，**不在 dependencies**

## 已知限制

- 处境判定使用词表匹配，不做语义理解；否定表达、复杂多意图和未知措辞仍可能误判。
- 不发 `inbox/claimed` 的旧宿主只能在首次装配之后使用 pre-step 兜底。
- 不同 agent 的状态隔离；没有 agent 身份的宿主只能在同一插件实例中共享无身份状态。
- 仅处理 `source.kind=user` 或旧宿主未提供 source 的消息；第三方通道若使用其他 source 标识真实用户输入，也会被忽略。
- `deferLoading` 的实际效果依模型适配器而异，故缺省关闭
- `mind_signals` 需要宿主有 `dsh-tools`；取不到就静默降级（工具不注册，
  其它功能不受影响），但会留 warn 日志 —— **静默降级过一次**，那次探针只报
  `mind.ok`，看起来一切正常
- 无 `icon` / `locale`，面板走默认图标与裸名回退
